# 변경 되돌리기와 복구 작업 흐름

- 작성일: 2026-09-16
- 분류: Git 학습 메모
- 상태: 일반화 완료

## 목적

변경을 되돌리는 작업은 단순히 이전 상태로 돌아가는 일이 아니다. 먼저 되돌릴 범위와 변경이 공유되었는지를 구분해야 한다. 작업 중인 파일만 되돌릴지, 이미 공유한 커밋의 영향을 상쇄할지에 따라 안전한 방법이 달라진다.

원본 프레젠테이션에서 확인한 핵심은 다음과 같다. 파일 단위 되돌리기는 작업자가 해당 파일을 수정하고 반영할 권한이 있을 때만 수행한다. 이 문서는 그 제약을 일반적인 Git 작업 절차로 정리한다.

## 되돌리기 전에 확인할 질문

1. 변경이 아직 커밋되지 않았는가?
2. 커밋은 했지만 원격 저장소에는 공유하지 않았는가?
3. 다른 사람이 받을 수 있는 브랜치에 이미 반영했는가?
4. 파일 전체를 되돌릴 것인가, 특정 줄이나 특정 변경만 되돌릴 것인가?
5. 해당 브랜치와 파일을 수정할 권한이 있는가?
6. 현재 작업 트리에 보관해야 할 다른 변경이 섞여 있는가?

마지막 질문을 건너뛰면 의도하지 않은 작업까지 함께 사라질 수 있다. 먼저 `git status`와 `git diff`로 변경 목록과 내용을 확인한다.

```bash
git status
git diff -- path/to/file
```

## 상황별 선택 기준

| 상황 | 권장 방법 | 결과 | 주의할 점 |
| --- | --- | --- | --- |
| 아직 커밋하지 않은 파일 변경 | 작업 트리의 해당 파일 복원 | 파일을 현재 커밋 기준 상태로 되돌림 | 같은 파일의 필요한 수정도 함께 사라짐 |
| 스테이징만 취소 | 스테이징 해제 | 파일 내용은 유지하고 인덱스에서만 제외 | 작업 트리 변경은 남아 있음 |
| 로컬 커밋을 수정해야 함 | 새 커밋 생성 또는 로컬 이력 정리 | 공유 전이라면 이력 조정 가능 | 이미 공유한 커밋은 이력 재작성 금지 |
| 공유된 커밋의 효과를 취소 | `git revert`로 상쇄 커밋 생성 | 기존 이력을 보존하며 반대 변경을 추가 | 충돌과 후속 변경 영향을 검토 |
| 특정 과거 버전의 파일만 가져오기 | 특정 커밋에서 파일 복원 후 새 커밋 | 다른 파일 이력은 건드리지 않음 | 복원 대상 버전과 현재 의존성 확인 |

## 파일 단위 복원 절차

파일 하나를 현재 커밋 상태로 되돌리는 경우에도, 바로 복원하지 말고 아래 순서로 확인한다.

1. 대상 브랜치와 작업 디렉터리가 맞는지 확인한다.
2. `git status`로 커밋하지 않은 변경을 목록화한다.
3. `git diff -- path/to/file`로 되돌릴 내용만 남아 있는지 읽는다.
4. 필요한 변경이 같은 파일에 섞였다면 별도 패치나 임시 커밋으로 보관한다.
5. 파일 복원을 실행한다.
6. 다시 diff를 확인해 대상 파일만 원하는 상태가 되었는지 검토한다.
7. 빌드, 테스트 또는 화면·데이터 확인처럼 변경 영향에 맞는 검증을 수행한다.

현재 커밋 기준으로 파일의 작업 트리 변경을 버리는 예시는 다음과 같다.

```bash
git restore -- path/to/file
git diff -- path/to/file
```

이 명령은 되돌리기 전 별도 보관을 만들지 않는다. 되찾아야 할 가능성이 있으면 먼저 내용을 복사하는 대신, 안전한 별도 브랜치에 임시 커밋을 만들거나 패치 파일로 보관하는 방식을 선택한다.

## 과거 버전의 파일을 복원하는 경우

현재 상태가 아니라 특정 시점의 파일을 가져와야 할 때는 커밋 식별자를 먼저 검토한다. 대상 파일의 이력을 확인하고, 복원 후보와 현재 파일의 차이를 읽은 뒤 적용한다.

```bash
git log --oneline -- path/to/file
git diff <target-commit> -- path/to/file
git restore --source=<target-commit> -- path/to/file
git diff -- path/to/file
```

여기서 `<target-commit>`은 검토를 마친 과거 커밋을 뜻한다. 복원 직후에는 새 상태가 작업 트리에만 있으므로, 테스트 후 의도가 분명한 새 커밋으로 남긴다. 과거 파일을 가져오는 행위가 현재 기능의 모든 의존성을 되돌리는 것은 아니다. 설정, 호출부, 데이터 형식이 함께 바뀌었는지 확인해야 한다.

## 공유된 변경은 상쇄 커밋으로 처리

다른 사람이 이미 받아갈 수 있는 커밋을 없애기 위해 강제로 이력을 되쓰면 협업 브랜치가 흔들릴 수 있다. 이 경우 기존 커밋을 지우지 않고 반대 변경을 만드는 `git revert`가 적합하다.

```bash
git show --stat <commit>
git show <commit>
git revert <commit>
```

`git show`로 먼저 영향 파일과 실제 변경을 확인한다. 되돌린 뒤 충돌이 나면 현재 코드가 왜 과거 변경과 달라졌는지 확인한다. 충돌을 기계적으로 해결하면 이후에 들어간 정상 변경까지 취소할 수 있다.

병합 커밋은 일반 커밋보다 판단이 어렵다. 어느 부모를 기준으로 되돌릴지에 따라 결과가 달라지므로, 병합 커밋을 되돌리기 전에는 브랜치 구조와 이후 반영된 변경을 검토하고 팀의 검토 절차를 따른다.

## 권한과 협업 경계

되돌리기는 기술적으로 가능하더라도 작업자가 임의로 실행하면 안 되는 경우가 있다.

- 보호된 브랜치나 공동 관리 파일은 정해진 검토·승인 절차를 따른다.
- 다른 작업자의 미완료 변경이 보이면 수정 범위를 합의한 뒤 진행한다.
- 파일 권한, 소유권, 배포 책임이 불명확하면 복원 명령을 실행하지 않고 담당자에게 확인한다.
- 복원 커밋 메시지에는 대상 범위와 되돌리는 이유를 적되, 고객 정보·접속 정보·운영 식별값은 넣지 않는다.

## 완료 확인

되돌리기 작업은 명령이 성공했다고 끝나지 않는다. 다음 항목을 확인한다.

- 변경 파일 목록이 의도한 범위와 일치하는지
- 되돌리려는 변경만 사라졌고, 보존할 변경은 남았는지
- 컴파일·정적 검사·자동 테스트 중 영향 범위에 맞는 검증을 했는지
- 화면이나 데이터 처리 흐름이 바뀌는 경우 수동 확인이 필요한지
- 공유 브랜치라면 코드 검토와 배포 전 검증 절차가 남아 있는지

## 기록할 내용

작업 기록에는 다음 정도면 충분하다.

- 되돌린 범위: 파일, 기능 또는 커밋 단위
- 선택한 방법: 작업 트리 복원, 과거 파일 복원, 상쇄 커밋
- 선택 이유: 미공유 변경인지, 공유된 변경인지
- 검증 결과와 남은 위험

실제 저장소 주소, 브랜치 이름, 사용자 계정, 내부 경로, 운영 환경 정보는 기록하지 않는다.
